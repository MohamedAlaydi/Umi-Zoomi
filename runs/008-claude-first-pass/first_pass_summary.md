## Seed and replicate noise

**Candidates with more than one Boltz-2 seed: 0.** Every run was submitted with `--num-diffusion-samples 1` and a single seed, and on disk every `boltz2/<qid>/` holds exactly one `seed_42/` with one `sample_1` triple. So the seed-to-seed SD of `iface_min` / `iface_mean` **cannot be computed from existing data**: there are no replicates at a second seed anywhere in the project.

What *can* be measured is the replicate SD for the same CDRH3 folded more than once at the same seed. Those pseudo-replicates split cleanly by whether the two runs shared a Boltz-2 template:

| kind | same template | rows (same CDRH3, same seed 42) | SD iface_min | SD iface_mean | range iface_min |
| --- | --- | --- | --- | --- | --- |
| cross-batch | **no** | 001:her2_cdrh3_3, 004:her2_cdrh3_3, 006:r004_cdrh3_3 | 0.001443 | 0.000144 | 0.002500 |
| within-batch | yes | 005:her2_anchored_13, 005:her2_anchored_31, 005:her2_anchored_6 | 0.000000 | 0.000000 | 0.000000 |
| cross-batch | yes | 004:her2_cdrh3_31, 006:r004_cdrh3_31 | 0.000000 | 0.000000 | 0.000000 |
| cross-batch | yes | 004:her2_cdrh3_4, 006:r004_cdrh3_4 | 0.000000 | 0.000000 | 0.000000 |

Two distinct numbers come out of that table, and they must not be conflated:

- **Same seed, same template → SD exactly 0.000000.** Boltz-2 is bit-reproducible: the three run-004 designs re-folded as run-006 controls reproduce run 004 to every printed digit on all eight score fields, and run 005's triplicated loop gives three identical rows. Batch composition (10 queries vs 44) changes nothing.

- **Same seed, different template → SD ≈ 0.0018, range 0.0025 on `iface_min`** (the single sequence shared by runs 001 and 004: `iface_min` 0.9355 vs 0.9330, `iptm` 0.965 vs 0.967, `plddt` 97.102 vs 97.132). n = 1 sequence, so this is an order of magnitude, not an estimate.

**Recommended noise floor, stated honestly:** the replicate floor is 0, the template-swap floor is ~0.003 on `iface_min`, and the seed floor is **unknown**. Since the whole run-006 shortlist is spread over about 0.14 of `iface_min` and the 8 candidates "above WT" beat it by 0.003–0.014, the margins that decide the shortlist are the same size as the one perturbation that has been measured. Until a second seed is run, do not treat an `iface_min` gap under ~0.01 as real. Getting the number is one short GPU job: re-fold ~10 run-006 candidates plus the WT at a second seed in one batch with the same template. Not done here (no GPU).

## (f) Caveats and handling recommendations

**1. Generator is confounded with every sequence gate, almost perfectly.** Run 004 (free loop) is 10/10 novelty-official and 0/10 grip. Run 005 (anchored) is 10/10 grip and 1/10 novelty-official. Run 006 (enumerated) is 40/40 on both, by construction — the enumeration *filtered on these very gates* before folding. Any "what do the passing candidates have in common" analysis over the pooled table recovers the generator setting, not biology. Stratify by run, or stay inside one run. The per-position tables in (d) are reported for both scopes for exactly this reason and neither should be read as an enrichment analysis.

**2. Run 006 has near-zero variance on everything except the interface.** All 40 enumerated candidates are novelty-legal, Cys-free, 4/4 grip, 2/2 liabilities, `p_high` in a 0.0056-wide band, `n_mut` 4–6. There is nothing to regress a pass/fail flag against inside that batch; `iface_min` is the only discriminator, and it spans roughly 0.77–0.92. Treat run 006 as a ranking problem on one noisy column, not a classification problem.

**3. Exact duplicates.** 90 rows share a CDRH3 with another row (46 rows are redundant). Three separate causes, all benign but all capable of inflating a count: (i) run 005 generated one loop three times in one batch; (ii) three run-004 designs were deliberately re-folded as run-006 controls; (iii) all 40 run-006 candidates are also rows of `legal-scored.csv`, which is where they were drawn from. Deduplicate on `cdrh3` before quoting any overall total — the `ALL` funnel row and the `cdrh3_n_rows_in_table` / `is_exact_dup` columns are there to make this visible.

**4. Threshold conflicts between the project's own files.** Four live disagreements, all preserved rather than silently resolved:

| min distance to provided | ≥ 2 | ≥ 3 | ≥ 2 (hard) | ≥ 3 (`MIN_DIST`) | ≥ 3 | both, as `novelty_official` and `novelty_margin` |
| max identity to trastuzumab | ≤ 70 % | ≤ 60 % | ≤ 70 % (hard) | ≤ 60 % (`MAX_IDENTITY`) | ≤ 60 % | both |
| cysteine | — | — | soft warning `ok, check C` | hard reject | excluded from the space | `has_cys` column + `FAIL_cys` gate |
| min pairwise diff | — | — | — | 2 (`--min-diff`) | 3 (`build_refold.py`) | not applied; diversity is a selection step, not a gate |

`report.py` prints `REJECTED` on the **official** rule only, so a design that `run.log` shows as `ok` can still be dropped by `rank.py`. Run 004's `her2_cdrh3_26` (dist 2) and run 005's `her2_anchored_14` (dist 2, 60 %) are exactly those cases, and they are the two rows where `novelty_official` is TRUE and `novelty_margin` is FALSE. A reader of `README.md` alone gets the looser bar.

**5. Seeds: the survey conflates two different seeds — corrected here.** `design/config.json` gives the **RFD4 generation** seed: 1 for runs 001/004/005, 2 for run 007. `boltz2/config.json` gives the **Boltz-2 refold** seed, and it is **42 for every run, 001 through 006**, confirmed three ways: the config files, the `seed_42/` directory names, and the `seed` column of every `refold_metrics.csv`. So the structural numbers are *not* separated by seed, and the survey's "seeds differ between tracks, 1 vs 42" caveat does not apply to anything structural. Chain layout is also identical everywhere (A 107 / B 120 / C 92 / D 17) as is `num_diffusion_samples 1`.

**5b. What *does* break cross-run comparability is the template, not the seed.** Each run's `prepared/holo/template.cif` is built from one of that run's own generated designs — the mmCIF data block is literally named `data_her2_cdrh3_3_template` in run 001 and `data_her2_cdrh3_21_template` in run 004 — so it is a per-run artifact, not a shared constant:

| run | template sha256 (16) | comparable to run 006? |
| --- | --- | --- |
| 001 | a234bcb48e5dbfb9 | no, different template |
| 004 | 719541a9bd7fb1cd | **yes, byte-identical** |
| 005 | 74d1eac1574bf611 | no, different template |
| 006 | 719541a9bd7fb1cd | **yes, byte-identical** |

`build_refold.py` copies run 004's template verbatim (`shutil.copy` from `REF_RUN`), so **runs 004 and 006 share a byte-identical template** and their numbers are directly comparable — proven, not assumed: the three `r004_*` controls reproduce their run-004 values exactly. Runs 001 and 005 each used a different template and are **not** strictly comparable to the run-006 wild type. The `wt_ref` column records this distinction as `in-batch` / `external-same-template` / `external-diff-template`, so the 10 run-004 rows borrowing the run-006 WT are flagged differently from the 12 rows of runs 001 and 005 that borrow it across a template change. Trust the external comparison for run 004; treat it as indicative only for runs 001 and 005.

**6. `min_ipae` and `binder_plddt` do not exist for run 006.** Those two columns come from the organisers' `refold-score`, which needs an RFD4 design folder; the enumerated candidates have none, which is why `collect_refold.py` was written against Boltz-2's own `scores.json` instead. The PAE `.npz` files were not kept and the `detailed_scores.cbor.gz` cannot be opened (no `cbor2` in either venv, and no network to add one). So run-006 rows have `min_ipae` and `binder_plddt` empty, and the complex-average `plddt` column is the only pLDDT comparable across all four runs. Do not rank across runs on `binder_plddt`.

**7. The interface gate needs an in-batch wild type, and only run 006 has one.** Runs 001/004/005 were submitted without a `trastuzumab_wt` arm, so `iface_min_minus_WT_batch` is empty for all 22 of their rows and the primary `group` label falls back to the run-006 WT with `wt_ref = external`. The `group_strict_wtref` column refuses that substitution and marks those rows `NA_no_inbatch_WT` instead, so both readings are on the table. Quote the strict column if the audience is the submission; quote the primary column for internal ranking.

**8. Neither `p_high` nor `iface_min` is an affinity measurement.** `p_high` is capped by the wild type at 0.998, so it cannot express "better than trastuzumab" and is a sieve, not an oracle. `iface_min` is folding confidence: 21 measured non-binders in the Champloo set score AF3 ipTM ≥ 0.7. The pre-registered PASS groups are therefore "worth spending a measurement on", not "predicted to bind better".

**9. Three of the six mutated positions are measured-intolerant.** G100 (OR 0.436), G101 (0.404) and D108 (0.221) all lose binding when mutated in the FACS data, and the enumerated shortlist mutates 4–6 of the six free positions. The design hypothesis treats all six as free because they make no HER2 contact; the measured data disagrees. A cheap follow-up that needs no GPU: re-rank the PASS set by how many intolerant positions it leaves at wild type.

**10. Run 007 is excluded.** `007-mohamed-anchored-diverse-k1` was still running on the GPU when this table was built (its `run.log` ends at "Dataset inference-dataset: 1 examples", no `manifest.csv`, no `refold_metrics.csv`, no `boltz2/` output). Re-run this script once it lands; it will pick the run up automatically only if a `manifest.csv` or `scored-boltz2/refold_metrics.csv` appears, which means `SOURCES` at the top of the script needs one line added.

**11. `F104` is a marginal anchor.** `interface_residues.csv` puts it in tier C: one atom contact at 4.5 Å, none at 4.0 Å, 6.2 Å² buried. It is weighted equally with W99/G103/Y105 in `grip_4of4` here, because that is what `report.py` and the anchored YAML do, but a `grip_3of4_no_F104` variant of the gate would free a position for almost no interface cost. Not applied — it would be tuning a pre-registered gate.
